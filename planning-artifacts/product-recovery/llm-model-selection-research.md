# LLM selection for evidence extraction and template matching

**Research checked:** 2026-10-19. This is a capability-based shortlist, not a claim that any model is more accurate than another. Compare candidates on a representative, adjudicated project-document golden set before selecting a production default.

## Recommendation

Run a small bake-off with **GPT-6 Luna** (efficient OpenAI candidate), **Claude Sonnet 5.5** (Anthropic), and **Gemini 4 Argon** (Google); optionally include **Mistral Large 3** as a Chat Completions-compatible alternative. Add **GPT-6 Astra** as a higher-cost OpenAI escalation candidate only if the golden-set results show Luna misses consequential, difficult cases. These are candidates because official docs expose relevant structured-output and document-input capabilities, not because vendor descriptions establish extraction superiority.

Keep the current workflow fail-closed: validate schema and field constraints, verify every evidence span against source text, and route missing/ambiguous/low-confidence or failed validation to human review. A second model may be tried for recoverable technical/semantic failures, but never treat valid JSON as proof of a true extraction or silently accept a disagreeing retry. The current application already has confidence/review behavior and source-excerpt verification in parts of the flow; preserve those safeguards.

**Current-repo compatibility caveat:** the application uses Ollama Cloud `gpt-oss:20b` by default, offers local Ollama and a configurable OpenAI-compatible Chat Completions endpoint. The compatible adapter maps `format: "json"` to `{ "response_format": { "type": "json_object" } }`; it does not send a JSON Schema. Ollama's official docs explicitly say Ollama Cloud currently does not support structured outputs, although its local API accepts a JSON Schema in `format`. Consequently, current production calls can request JSON shape but cannot obtain provider-enforced conformance to the application's actual schema. The compatible endpoint is a practical path to test Mistral Large 3's JSON mode, but switching vendor/model alone does not enable strict schema enforcement. OpenAI GPT-6 models do support Chat Completions and Structured Outputs, but the current adapter would need to send the documented JSON Schema response format to use that guarantee; Anthropic and Gemini have their own documented APIs. (Repo: `src/lib/ai/ollama.ts`, `.env.example`; [Ollama Structured outputs](https://docs.ollama.com/capabilities/structured-outputs), accessed 2026-10-19.)

The document worker has an independent adapter in `worker/src/services/document-extraction.ts`: `configuredModelProvider()` defaults to local Ollama when unset, and `requestModel()` uses JSON-object mode for the OpenAI-compatible branch and JSON mode for Ollama Cloud rather than a provider-enforced application schema. It does not route through `src/lib/ai/ollama.ts`. Evaluate and configure both paths before treating a model binding or structured-output capability as an application-wide contract.

## What structured output does—and does not—guarantee

A provider's schema-constrained decoding can enforce representational constraints (valid JSON, required keys/types, and supported enum/schema rules). It does **not** establish that a value is present in the evidence, correctly interpreted, assigned to the right template field, or supported by a citation. Those are semantic/evidence correctness questions and require task-specific validation and evaluation. An application must also account for refusals, truncation, unsupported schema features, and provider/request errors rather than treating every response as a valid extraction.

For this task, benchmark at least: field-level exact/normalized match; correct “not stated”/unknown handling; template-category assignment; source-span correctness (exact quotes and page/section references); false-positive rate on absent facts; multilingual (including Bahasa Indonesia/English and mixed-language) documents; scanned/OCR and tables; schema/enum compliance; abstention/review rate; and end-to-end latency/cost for the app's realistic chunk sizes. Stratify by document type and difficulty; adjudicate a held-out set and compare per-field/per-category errors, not only a single aggregate score. Keep a fixed schema and prompt version during comparisons.

## Suggested rollout / routing

1. **Baseline and candidates:** evaluate the current `gpt-oss:20b` pipeline and GPT-6 Luna, Claude Sonnet 5.5, Gemini 4 Argon, and (optionally) Mistral Large 3 on the same golden set. First confirm the deployed endpoint actually supports the requested structured-output feature; log schema-validation failures separately from semantic failures.
2. **Choose on measured trade-offs:** select a primary only if it meets predefined field/evidence precision and recall plus review-rate targets. Favor cost/latency only after the quality gates are met; model cards do not predict this application's score.
3. **Fail safe:** schema parse/validation error, unsupported request, timeout, missing evidence, citation mismatch, or low confidence → no accepted extraction; retry once on an approved stronger candidate only for recoverable errors, otherwise send to human review. If providers disagree on a consequential field, surface the conflict for review. Never promote a fallback answer merely because it parses.
4. **Re-evaluate:** pin model identifiers where supported, record model/prompt/schema version, and rerun the golden set when any changes. Review data-retention, regional processing, and document-sharing requirements before sending project evidence to a new cloud vendor.
